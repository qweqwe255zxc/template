# Аудит готовности к сдаче

Ты проверяешь конкретный проект, собранный на этом шаблоне (Next.js App Router, конфиг-driven секции, токены в `theme/tokens.css`), на пригодность отдать клиенту за деньги.

## Как себя вести (обязательно)

- **Жёстко и по делу.** Никаких «в целом хорошо», «отличная работа», «есть небольшие моменты». Ценность отчёта — в найденных дефектах. Если всё правда чисто, так и скажи одной строкой и покажи, что именно проверил.
- **Не догадываться.** Каждый пункт отчёта подтверждён прочитанным файлом, выводом grep, замером в браузере или скриншотом. Формулировки «вероятно, сломается» допустимы только с явной пометкой `(не проверено: причина)`.
- **Взгляд платящего клиента.** Он не читает код. Он открывает сайт на своём телефоне, показывает партнёру на ноутбуке и открывает на офисном мониторе 1920. Всё, что там выглядит несуразно, — дефект, даже если код формально верен.
- **По умолчанию не чинить.** Сначала полный отчёт. Правки — только если попросили («почини», «исправь», «--fix») или после явного согласия на план. Тогда чинить строго по приоритету из отчёта и по планке качества §1.5 CLAUDE.md.
- **Каталог вариантов — товар.** Никогда не предлагай «удалить дубликаты вариантов» как способ починки.

## Что читать перед началом

`CLAUDE.md` (§1.5 — планка качества, §2 — каталог вариантов, §3 — ритм поверхностей, §6 — запреты). При работе с секциями — навык `section-system`, при работе с глубиной/тарифом — `presets`. Аудит проверяет соответствие именно этим правилам, а не абстрактному «best practice».

## Фаза 0. Ворота сборки

Без этого дальше идти нет смысла — если проект не собирается, всё остальное косметика.

```bash
npm run typecheck
npm run build 2>&1 | tail -40
```

Затем подними дев-сервер (`npm run dev`, обычно `http://localhost:3000`) и держи его до конца аудита: фазы 2 и 4 без него не выполняются.

Ловушка: `npm run build` проходит, а страница падает в рантайме на клиентском компоненте. Главную (`/`) и `/qa-audit` открыть обязательно и прочитать консоль.

## Фаза 1. Конфиг проекта — это ли проект клиента

Читай `content/site.config.ts`, `theme/tokens.css`, `theme/palette.ts`, `app/layout.tsx`.

1. **Палитра не дефолтная.** `--palette-accent: #16494f` и `--palette-paper: #f4f2ee` — цвета демо-сборки «Модуль». Если они остались (или остались близкие к ним — палитру «подвинули», а не собрали заново), это блокер: клиенту отдают чужой бренд. Там же проверяй шрифтовую пару: Wix Madefor Display / Wix Madefor Text + Golos Text — это тоже демо.
2. **Палитра синхронизирована в двух файлах.** `theme/tokens.css` и `theme/palette.ts` (рантайм-дубль для favicon/OG/`themeColor`). Расхождение — блокер: OG-картинка и цвет вкладки будут от другого бренда.
   ```bash
   grep -nE "palette-(paper|surface|ink|accent)\b" theme/tokens.css | head
   grep -nE "(paper|surface|ink|accent):" theme/palette.ts | head
   ```
3. **Шрифты подключены и с кириллицей.** В `app/layout.tsx` — `next/font/google`, в `subsets` обязателен `"cyrillic"`. Гарнитура без кириллицы (Syne, Space Grotesk и подобные) на русском тексте даёт подстановку системным шрифтом — визуальный брак.
4. **Варианты секций проставлены.** Секция без `variant` берёт дефолт пресета; если пусто у всех — сайт собран из дефолтов.
   ```bash
   grep -nE "type: \"|variant: \"|surface: \"" content/site.config.ts
   ```
5. **Ритм поверхностей (§3 CLAUDE.md).** Выпиши порядок `surface` подряд идущих секций. Дефекты: три и более подряд `paper`/`surface` без `ink`/`accent`; больше одного `ink`; больше одного `accent`; вообще ни одного тёмного или акцентного блока.
6. **Штампы (§6 CLAUDE.md).** `hero` с `variant: "split"` + `widget`, если это не ключевая метрика бренда. Одинаковый вариант у всех секций подряд там, где это не семейство `sticky-split`.
7. **`sticky-split` — всё или ничего (§2.13).** Если приём применён к части секций, это дефект: одинокая залипающая секция читается как сбой.
8. **Пресет выбран осознанно.** `theme.preset` — `econom` или `standard`. Шаблон знает только эти два тарифа. Если стоит `standard`, но карточки визуально не отличаются от фона — см. фазу 2, п. «карточка отличима от фона».
9. **Контент — не рыба.** Ищи остатки демо-текста: «Лорем», «Компания», «example.ru», `+7 (999) 000-00-00`, «Иван Иванов», пустые `href`. Телефон, почта, адрес, ИНН, ссылка на политику должны быть настоящими.

## Фаза 2. Адаптивность и вёрстка — глазами, а не по коду

**Стенд.** `/qa-audit` — страница со списком, `/qa-audit/<секция>` рендерит все варианты секции подряд с зелёными подписями. Проверять и главную (`/`, реальная сборка клиента), и стенд (все варианты каталога, если аудит шаблона).

**Ширины обязательны все пять: 390 / 768 / 1024 / 1440 / 1920.** Инструменты: `mcp__claude-in-chrome__resize_window` + `computer` (скриншот) + `javascript_tool` (замеры). Пробы для копирования — в `references/probes.md`.

Порядок на каждой ширине:
1. Прогнать пробу горизонтального переполнения. Любой `scrollWidth > clientWidth` на body — блокер.
2. Снять скриншот и **посмотреть на него**. Числа не ловят «смотрится несуразно»: заголовок в четыре слова колонкой, кнопка шире карточки, фото в соседних карточках на разной высоте, дыра в сетке из-за неполного последнего ряда.
3. Прогнать пробу выравнивания рядов там, где есть сетка карточек.

Что считается дефектом (планка §1.5 CLAUDE.md, каждый пункт — отдельная категория в отчёте):

- **Сетка не перестраивается.** 4→2→1 обязательно. Четыре колонки, сжатые до 180px на планшете, — дефект, даже если ничего не переполняет.
- **Текст молча теряется.** `line-clamp`, `truncate`, `overflow: hidden` на пользовательском тексте запрещены: текст пишет клиент, и он не узнает, что половину съело.
  ```bash
  grep -rn --include="*.tsx" -E "line-clamp|truncate|text-ellipsis" components
  ```
  Разбирай каждое попадание: `truncate` на служебной подписи в футере — обсуждаемо, `line-clamp-2` на описании кейса — дефект.
- **Фиксированные размеры.** `h-[34rem]`, `min-h-[420px]`, любое значение, выведенное из `--container-page`. Высота медиа — `aspect-*`, ширина — колонка сетки.
  ```bash
  grep -rn --include="*.tsx" -E "\b(h|min-h|max-h|w|min-w)-\[[0-9]" components
  grep -rn --include="*.tsx" "container-page" components
  ```
  Ложные срабатывания, которые дефектом не являются: `max-w-[46ch]`, `max-w-[36rem]` на абзаце — это мера строки, а не фиксированный размер блока. Отсекай их вручную, не тащи в отчёт.
- **Внутри ряда не выровнено.** Карточки одного ряда одной высоты, их иконки/заголовки/фото/кнопки — на одних линиях.
- **Центрирование по колонке вместо секции.** Самая частая незаметная ошибка: заголовку с `max-w-*` забыли `mx-auto`.
  ```bash
  grep -rn --include="*.tsx" -E "text-center" components | grep -E "max-w-" | grep -v "mx-auto"
  ```
- **Кнопки в группе разной ширины.** Должно быть `w-full` в колонке + `sm:w-auto sm:min-w-*`.
- **Карточка не отличима от фона** в текущем пресете. В `econom` — рамка, в `standard` — поверхность плюс рамка. Одна тень не считается: на светлой секции её не видно.
- **Хардкод вместо токенов.** Ни один компонент не содержит hex, px-размера шрифта, тени или радиуса.
  ```bash
  grep -rn --include="*.tsx" --include="*.ts" -E "#[0-9a-fA-F]{3,8}\b" components lib
  grep -rn --include="*.tsx" -E "shadow-\[|rounded-\[|text-\[[0-9]" components
  ```

Отдельно проверь **тёмную тему** (`ThemeToggle`) и `prefers-reduced-motion`: переключи и пройди те же ширины хотя бы на 390 и 1440. Секции `ink`/`accent` в тёмной теме — частое место, где контраст уезжает.

## Фаза 3. Законченность и тупики

1. **Форма заявки** (`components/sections/ContactForm`, `app/api/contact/route.ts`). Проверить руками в браузере, не по коду: состояние отправки (кнопка блокируется?), успех (что видит пользователь?), ошибка сети/500 (есть ли внятное сообщение или форма молча ничего не делает?), валидация (сообщения под полями, читаемые, на русском), маска телефона, чекбокс согласия и ссылка на политику.
2. **API-роут переживает отсутствие ключей.** `.env.local` может быть пустым — по замыслу заявка тогда печатается в лог. Убедись, что это так и что пользователю всё равно показывается успех, а не ошибка.
3. **Тупики.** `href="#"`, `href=""`, кнопки без обработчика, пункты меню, ведущие в никуда, якоря на несуществующие `id` секций.
   ```bash
   grep -rn --include="*.tsx" --include="*.ts" -E 'href="(#|)"' components app content
   ```
   Сверь `nav`-ссылки вида `#id` с `id` секций из `site.config.ts` — рассинхрон даёт кнопку, которая никуда не скроллит.
4. **Служебные страницы.** `/privacy`, 404 (`app/not-found.tsx`), `app/robots.ts`, `app/sitemap.ts`, `app/opengraph-image.tsx`, `app/icon.svg`. Открыть каждую. OG-картинку проверить на реальный домен и цвета бренда.
5. **Метаданные.** `lib/seo.ts` + `buildMetadata`: title, description, canonical, OG — от клиента, а не от демо. `lang="ru"` в `app/layout.tsx`.
6. **Метрика.** `YandexMetrika` — либо настоящий счётчик, либо отключено. Демо-номер в проде — дефект.
7. **Доступность по минимуму.** `focus-visible` виден на кнопках, ссылках, полях (пройди страницу табом); у изображений осмысленный `alt`; аккордеон FAQ управляется с клавиатуры; иконки-кнопки имеют `aria-label`.
8. **Консоль чистая.** Открыть `/` и `/qa-audit/<пара секций>`, прочитать консоль. `console.warn` из секций — это дев-предупреждения шаблона о неверном конфиге (например, `split` hero без фото молча падает в `type-only`): каждое такое предупреждение = ошибка в `site.config.ts`, тащи в отчёт с точным текстом.
   ```bash
   grep -rn --include="*.tsx" --include="*.ts" "console\.log" components app lib
   ```
9. **Мусор в репозитории.** `repomix-output.xml`, `.DS_Store`, `tsconfig.tsbuildinfo`, временные стенды в `app/`, файлы `.claude/worktrees` — что из этого не должно уехать клиенту и что не закрыто `.gitignore`.

## Фаза 4. Документация против кода

1. **`README.md`.** Сверь с реальностью: команды из `package.json`, шаги запуска, требуемые переменные окружения, заявленные возможности. Пустой или однострочный README для товара, который продают, — дефект уровня «не готово к сдаче».
2. **`.env.example`.** Каждая переменная, которую читает код, описана; описанных, но не читаемых кодом, нет.
   ```bash
   grep -rn --include="*.ts" --include="*.tsx" "process\.env\." app lib components | sed -E 's/.*process\.env\.([A-Z_]+).*/\1/' | sort -u
   ```
3. **`CLAUDE.md` и `docs/`.** Каталоги вариантов в §2 CLAUDE.md и `docs/section-system.md` должны совпадать с реальными файлами в `components/sections/*/variants/`. Расхождение — прямая причина будущих багов: агент выберет несуществующий вариант.
   ```bash
   ls components/sections/*/variants/
   ```
   Где документ спорит с кодом — **прав код**, а документ нужно поправить (это отдельный пункт плана).

## Фаза 5. Гигиена и безопасность

1. Секреты в коде: токены, ключи, chat_id, пароли — ничего этого не должно быть вне `.env.local`.
   ```bash
   grep -rnE "(sk-|re_|bot[0-9]{6,}:|AIza)[A-Za-z0-9_-]{10,}" --include="*.ts" --include="*.tsx" --include="*.mjs" . --exclude-dir=node_modules --exclude-dir=.next
   ```
2. `.env.local` в `.gitignore`; в истории коммитов нет закоммиченных ключей.
3. Антибот и рейт-лимит в `app/api/contact/route.ts` на месте, пороги не обнулены.
4. `TODO`/`FIXME`/`ХАК` в боевых путях.
   ```bash
   grep -rn --include="*.tsx" --include="*.ts" -E "TODO|FIXME|XXX|ХАК" components app lib
   ```

## Режим починки

Включается только по явной просьбе. Тогда: чинить сверху вниз по плану, каждую правку доводить до планки §1.5 (пять ширин, ничего не теряется, без фиксированных размеров, ряд выровнен, проверено глазами), после каждой группы правок — `npm run typecheck` и повторный проход стенда на 390 и 1440. Не удалять варианты и не «упрощать» каталог. В конце — короткий список того, что починено, и что осталось нетронутым и почему.
